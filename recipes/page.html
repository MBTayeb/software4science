The word 'algorithm' comes from Algorithmi, the Latinized form of Muhammad ibn Musa al-Khwarizmi's name (c. 780–850). In software engineering, the term refers to a concrete recipe that solves a problem in a finite number of steps. It's the essence of software engineering, especially in RSE, where much of the work involves data processing, calculations, and visualizations.

Because of the importance of algorithms in RSE, we want to make sure that they are of high quality and efficiency so that the algorithm finishes in a reasonable amount of time regardless of the size of the problem. We achieve this by analyzing algorithms quantitatively, focusing on what matters rather than the tiny details. That analysis lets us classify algorithms according to their input size using the Big-O notation, which gives us what's known as the time complexity of the algorithm. The higher that complexity, the worse the algorithm scales as the data grows, and past a certain point, it may simply never finish.

When studying space complexity, we focus on how much extra memory an algorithm requires beyond the input data itself. This is critical in research computing, where exceeding memory limits can trigger out-of-memory errors and fail long-running cluster jobs.

When designing an algorithm, you'll frequently trade memory for speed, using extra storage to avoid repeating expensive computations. It's a decision to make based on your hardware constraints, dataset size, and the nature of the problem.

To get a preliminary feel for how different complexities scale, we plot their growth curves. In Figure 1, both axes are constrained equally so that a simple linear relationship forms an exact diagonal baseline. This equal ratio gives us a visual benchmark. Anything curving above the diagonal is a warning sign, it grows faster than your input size, meaning it'll slow you down more and more as your data scales up. Anything below the diagonal is the opposite: it grows slower, so scaling up your data barely touches its runtime.

However, forcing equal axes makes it hard to see the true gap between these curves. In Figure 2, allowing the vertical axis to auto-scale highlights the stark contrast. The exponential curve shoots straight up, completely dominating the plot and squishing every other line toward the bottom.

Because the exponential curve distorts the view, Figure 3 removes it entirely. With the extreme outlier out of the way, auto-scaling opens up the plot, making it easy to compare the remaining growth shapes side by side. Consider this a quick preview of how vastly different scaling behaviors can be.

Data types

Algorithms don't operate in a vacuum, which is why they are traditionally taught alongside data structures. While an algorithm defines the steps to solve a problem, data structures define how information is organized. That structure directly shapes how fast your algorithm can run. Data structures are themselves composed of many smaller elements, each holding its own kind of value, be it a number, a piece of text, or something else.

To keep our analysis general, we focus on abstract data types rather than data language-specific code. An abstract data type defines what operations you need, not how to implement them. Many different data structures can fulfill that same model. Understanding abstract data types helps you weigh time and space trade-offs, making it much easier to pick the right data structure for your problem.
