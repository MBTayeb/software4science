What are data types?

Imagine watching a long-running data simulation crash at 2 AM because 0.1 + 0.2 evaluated to 0.30000000000000004. The hardware isn't broken, it's just executing the unforgiving, precise logic of memory representation.

This connects back to space complexity in the algorithm chapters, which lets us reason about memory usage. But space complexity isn't the whole story. The type of each element also determines the memory use of the whole structure, and how those bits get read back out.

While programming, we deal with different kinds of data, be it text or numbers. But at its core, every piece of data in computers is composed of bits, i.e. ones and zeroes. In other words, the underlying hardware represents all programming data using binary digits.

Bits are collected in memory in bytes, i.e. a unit of eight bits. Indeed, bytes are the smallest addressable unit of memory. Since 8 bits with two states each can only represent 2 ^ 8 = 256 cases, they are not enough for all numbers. Thus, the representable data depends on the number of used bytes. Hence, the data type dictates how many bytes each element occupies.

Now, representing positive whole numbers with binary digits in a byte is simple.

Decimal Binary
000 0000 0000
001 0000 0001
002 0000 0010
003 0000 0011
004 0000 0100
005 0000 0101
... ...
254 1111 1110
255 1111 1111

But what about negative numbers? Decimal values? Text? None of these fit cleanly into plain binary: they demand far more complex patterns. Without a defined data type telling the system how to interpret those raw bits, the data could mean anything.

We can introduce some basic types: Booleans which represent a logical state, i.e. true or false Integers which represent whole numbers Floats which represent decimal numbers Chars which represent a single character Strings which represent a string of characters

Each of these types comes in different sizes, measured in bytes. More bytes means more possible bit patterns, so more values can be stored exactly. Single precision floats use 4 bytes, doubles use 8, and the extra bytes give doubles more precision and a wider range of values. Exactly how many bytes a given type uses varies between programming languages, and even between implementations of the same language.

The byte 1100 0001 can mean an unsigned integer of 193, a signed integer of -63, or the Latin-1 character 'Á' depending on the reader's assumptions. Interpreted as an E4M3 float, that identical bit pattern becomes -2.25. Four distinct interpretations from a single sequence of bits prove a fundamental truth of computing: raw memory is meaningless without a data type to decode it.

Back to the crash from the opening: 0.1 is one of the values that doesn't fit exactly: it has no exact binary representation, the same way 1/3 has no exact decimal one, it repeats forever. The float stores the closest approximation that fits in its bits. 0.2 gets the same treatment. Add the two rounded values together, and the errors surface as 0.30000000000000004. Thus, the crash is normal and the programmer should take rounding errors in consideration.

Minifloats are small floating-point formats used when dealing with large data structures that don't need much precision. While standard floats usually take 4 to 8 bytes, machine learning's demand for lower precision has produced two-byte, one-byte, and even half-byte (nibble) formats. They sacrifice precision and range for big savings in memory and bandwidth.

Static vs dynamic programming languages

Now, there are languages that require fixing the type of a variable when defining it. In other words, the type of a variable can't be changed once it's defined. These are static programming languages. On the other hand, dynamic programming languages allow this.

Dynamic typing makes programming simpler to beginners, as many things are done automatically. But, this could lead to type errors that are hard to catch. Static programming makes programming a bit harder, but has the reward of avoiding such errors by default and getting results faster.

Type hints - Gradual typing

To get the best of both dynamic and static languages, many dynamic languages have begun allowing type hints. These are optional type specifications that help catch bugs before runtime. In other words, projects built with dynamic languages can gradually include type hints without affecting the execution of the code. Because type hints are ignored at runtime, mistakes won't crash your program. Instead, IDEs run type checkers behind the scenes to flag errors in your editor as you write code.

Gradually introducing types to an existing project is not trivial. It might look simple for small programs, but once the code gets larger and different cases need to be considered, it becomes hard to get your head around what type each object in the code is. Because of this, it might take some time to fix all the type errors flagged by the type checker (chatbots might be helpful here). Still, it is reassuring to know that these errors don't stop the code from functioning.

Type checkers are similar to linters: both analyze your code statically, i.e. without running it. Type checkers look for type errors; linters look for other kinds of issues (style, unused code, suspicious patterns, potential bugs).
